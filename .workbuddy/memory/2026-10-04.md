## ★★ 用具体数据走通全流程时的重大发现：**明细分摊会算出「负数」**

用户要"按整个流程带他梳理一遍，要有数据"。我用一套完整数据（3 商品 100/100/100 + 5 张券）把 6 步全走了一遍，
在算**方案 `[B,C,A]`** 时发现：

```
① 券B(满200减100,只作用商品2/3)：折后 200 ≥ 200 → 减 100；明细 {2:5000, 3:5000}
② 券C(满80减20,只作用商品1)   ：100 ≥ 80 → 减 20；明细 {1:2000, 2:5000, 3:5000}
③ 券A(每满100减20,作用全部)   ：折后 = 8000 + 5000 + 5000 = 18000
   每满100 → 只减 1 次 → discount = 2000
   按讲义算法分摊（分子用【原价】、分母用【折后总价】）：
      商品1 = 2000 * 10000 / 18000 = 1111
      商品2 = 2000 * 10000 / 18000 = 1111
      商品3 = 2000 - 1111 - 1111 = 【-222】 ❌ 负数！
```

**★ 这是 2026-10-03 记的「口径不一致」观察的升级 —— 之前以为是"分配不均"，实际会算出负数。**
- 根因：分子之和（原价 30000）> 分母（折后 18000），**比例之和 = 1.67 > 1**
  ⇒ 前几件就"超支"了 ⇒ 余额落给最后一件，**可能为负**
- **总优惠金额仍然正确**（`dto.discountAmount` 是独立累加的，不受分摊影响）
- **但单件明细为负 = 相当于给那件商品"加价"** ❌ 业务上荒谬；**退款按实付退 → 会算错钱**
- **在真实业务里很容易踩到**：只要各券的**适用商品范围不同**，折后价差异就会拉大
- **修法**：分子也用折后价 ⇒ `discountAmount * (course.getPrice() - detailMap.get(course.getId())) / totalAmount`
  此时 `Σ分子 == 分母` ⇒ **比例之和 = 1** ⇒ 最后一件必然 ≥ 0 ✅（已用同例验证：888/555/557）

**仍按惯例处理**：说清"事实 + 推演 + 影响 + 修法"，**不直接断言讲义写错**（它可能是有意简化）。

## day12 2.6「CompleteableFuture 并发计算」代码分析（用户要求）

**改动两处**：① `PromotionConfig` 加线程池 `discountSolutionExecutor`；② `findDiscountSolution` 第 4 步改为并行 + `CountDownLatch` 等待。

### 线程池配置（讲义）

```java
@Bean
public Executor discountSolutionExecutor(){
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(12);      // 核心线程数
    executor.setMaxPoolSize(12);       // ★ 和核心相同 → 不想扩容
    executor.setQueueCapacity(99999);  // ★ 队列极大
    executor.setThreadNamePrefix("discount-solution-calculator-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());  // ★ 抛异常
    executor.initialize();             // ★ 多余（InitializingBean 会自动调）
    return executor;
}
```

### 主方法第 4 步（讲义）

```java
List<CouponDiscountDTO> list = Collections.synchronizedList(new ArrayList<>(solutions.size()));
CountDownLatch latch = new CountDownLatch(solutions.size());
for (List<Coupon> solution : solutions) {
    CompletableFuture
            .supplyAsync(() -> calculateSolutionDiscount(availableCouponMap, orderCourses, solution),
                         discountSolutionExecutor)
            .thenAccept(dto -> { list.add(dto); latch.countDown(); });
}
try { latch.await(1, TimeUnit.SECONDS); }
catch (InterruptedException e) { log.error("优惠方案计算被中断，{}", e.getMessage()); }
// TODO 5.筛选最优解  return null;   ← 2.7 才补第 5 步
```

### 🔴 发现的 4 个真实隐患

**① `thenAccept` 在任务异常时不执行 → `countDown` 漏调 → latch 永不归零**
`supplyAsync` 的 supplier 抛异常 → future 异常完成 → **`thenAccept` 不执行** → 既丢结果也不 countDown。
⇒ `latch.await(1s)` 必然等到超时，且结果集缺项。
**修法**：改用 **`whenComplete((dto, ex) -> { if (ex != null) log.error(...); else list.add(dto); latch.countDown(); })`**。

**② `latch.await(1, TimeUnit.SECONDS)` 三宗罪**
- 写死 1 秒（方案多时可能不够）
- **忽略返回值（boolean）** → 不知道是否超时
- **超时后主线程继续遍历 list，而子线程还在 `list.add`** →
  `Collections.synchronizedList` 只保证单方法原子，**遍历时不加锁** → **ConcurrentModificationException** ❌

**③ `catch (InterruptedException e)` 里没有恢复中断标志**
标准反模式，应补 `Thread.currentThread().interrupt();`

**④ `queueCapacity=99999` + `AbortPolicy` 的组合很危险**
- 超大队列 ⇒ 延迟拒绝、任务堆积、内存风险
- `AbortPolicy` 在 `for` 循环里抛 `RejectedExecutionException` ⇒ **中断整个循环**，后面方案全不算；
  而 `latch` 初值已是 `solutions.size()`，**剩下的 countDown 永远不会来** ⇒ 必然超时
- ⚠️ **和项目另一个池不���致**：`generateExchangeCodeExecutor` 用的是 `CallerRunsPolicy`（不丢任务、形成背压）

### ⚠️ 其他可商榷点
- `corePoolSize == maxPoolSize == 12`：不想扩容是对的（纯 CPU 计算），但 **12 是魔法数字**，
  应按 `Runtime.getRuntime().availableProcessors()` 设
- `executor.initialize()` 多余（`ThreadPoolTaskExecutor` 实现了 `InitializingBean`）

### ★ 一个重要的观察：这里其实可以不用 `CountDownLatch`

`CompletableFuture.allOf(futures).join()` 一行就能等全部完成，而且**能传播异常**：
```java
CompletableFuture<?>[] fs = solutions.stream()
        .map(s -> CompletableFuture.supplyAsync(() -> calculateSolutionDiscount(...), executor)
                                   .thenAccept(list::add))
        .toArray(CompletableFuture[]::new);
CompletableFuture.allOf(fs).join();
```
**那讲义为什么用 CountDownLatch？** —— 因为**面试题 4.4 就是考 CountDownLatch 原理**，
讲义是刻意用它的（教学/面试导向）。技术上 `allOf` 更简洁 ✅（这个观察值得讲给用户）。

### ✅ 做对的地方
- `supplyAsync(..., executor)` **显式指定自定义线程池** ⇒ 不占用 `ForkJoinPool.commonPool()`（不和其他业务抢）
- `CountDownLatch` 等一批任务 —— 它的经典用法
- `Collections.synchronizedList` 保护并发写
- 把 `calculateSolutionDiscount` 抽成**参数自包含**的方法 ⇒ 才能安全并发
