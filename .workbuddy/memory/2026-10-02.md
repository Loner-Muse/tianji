## 答疑：为什么生成兑换码时只把「券 → 最大序列号」缓存到 Redis？

用户问（讲义 3.1 的原文表述）："为什么生成兑换码时，将优惠券及对应兑换码序列号的最大值缓存到Redis中"。

**根本目的：从 serialNum 反推 couponId，避免查 DB**（`exchangeCoupon` 异步化后校验阶段不能再碰 DB）。详见 2026-09-28 的 3.1 笔记。

### 为什么"一个最大值"就够了 —— 因为号码是「整段分配」的
`serialOps.increment(totalNum)` **一次向 Redis 申请一整段连续号**，所以每张券占用的号码永远是一段**连续、不重叠**的区间：
```
券A 分到   1 ~ 6000     → 只需存一个数：6000
券B 分到 6001 ~ 12100   → 只需存一个数：12100
```
**一个数 = 一段区间 = 这张券的全部兑换码。**

### 为什么存的是「最大值」而不是「起点」
1. 最大值是**号段上界**，天然表达"这张券的码到这里为止"
2. 反查取法是「找 `score ≥ serialNum` 的**第一个**」—— 正好需要上界（用起点就得反着取最后一个，不直观）
3. **生成时顺手就有**：`increment(totalNum)` 的返回值就是它，不用额外算

### 为什么用 ZSet 而不是 Hash
因为查询方式是**按 score 做范围查找**（`ZRANGEBYSCORE`）。Hash 做不到按 value 排序范围查；
若用 Hash 就得把每张券的区间全读出来在内存里比 —— 不可行。

### 反查的正确性（不变式）
号码连续、不重叠 → 「第一个 score ≥ serialNum 的成员」**必然是覆盖 serialNum 的那张券**。
验证：`serialNum=3000 → [A:6000]` ✅；`6000 → A` ✅；`6001 → B` ✅；`13000 → 无 → null` ✅

### ⚠️ 讲义实现的脆弱点（再次强调）
讲义把 max 写成 `serialNum + 5000`（经验值）。语义上要的是"**score 不小于 serialNum 的第一个**"，
**本来就不需要上界** → 应直接用 `Double.POSITIVE_INFINITY`。
若某张券 `totalNum > 5000`，号段跨度超出 5000 后反推会失败（返回 null → 误报"兑换码不存在"）。

## 答疑：`rangeByScore` 为什么用 `Set` 接收？

用户问讲义 `exchangeTargetId` 里 `Set<String> results = ...rangeByScore(...)` 为何用 Set。

**答：Spring Data Redis 的 API 定义就是这样 —— ZSet 的语义本身就是「集合」（Sorted SET）。**

**javap 证据**（spring-data-redis 2.7.18）：
```
public abstract java.util.Set<V> range(K, long, long);
public abstract java.util.Set<V> rangeByScore(K, double, double, long, long);
public abstract java.util.Set<V> reverseRange(K, long, long);
... 所有 range* 方法都返回 Set<V>
```
→ 不是这一个方法的特例，是**统一约定**：ZSet 的 member **唯一**（score 可重复），`Set` 正好表达"成员不重复"。

**★ 最关键的一点：底层实际是 `LinkedHashSet`（顺序保留）**
`javap -c DefaultZSetOperations` 里数到 **10 处 `java/util/LinkedHashSet`**。
→ Redis 返回的数据本身按 score 升序，`LinkedHashSet` 又保序 ⇒ **`iterator().next()` 就是 score 最小的那个** ✅
→ **如果换成 `HashSet`，顺序不保证，"取第一个"就变成"随机取一个"，整个反推逻辑就崩了。**
（这是个隐式依赖：代码能跑对，靠的是 Spring Data 用了 LinkedHashSet。）

**实操注意**：`Set` 没有 `get(int)` → 取第一个要用 `iterator().next()`（或 Java 21 的 `getFirst()`）。
等价写法：`results.stream().findFirst().map(Long::parseLong).orElse(null)`

**顺带**：`rangeByScore` 的 min/max 是 `double`，传 `long serialNum` 会自动转 double ——
`double` 精确整数上限 2^53 ≈ 9×10^15，序列号远小于它，**无精度风险**。

## day11 3.2 兑换码 LUA 脚本走读（发现 1 个真 bug）

用户贴了课件的 `exchange_coupon.lua` 让解释。

**输入约定**：`KEYS[1]=coupon:code:map`(BitMap)、`KEYS[2]=coupon:code:range`(ZSet)；
`ARGV[1]=serialNum`、`ARGV[2]=serialNum+5000`、`ARGV[3]=userId`

**流程**：GETBIT 判重 → ZRANGEBYSCORE 反查 cid → EXISTS 券缓存 → 校验 issueEndTime → 限领 HINCRBY+判断 → 最后才 SETBIT 占位 → 返回 cid。
错误码：`"1"`=已兑换 / `"2"`=码不存在 / `"3"`=券缓存不存在 / `"4"`=活动已结束 / `"5"`=超出限领。

### 🔴 真 BUG：时间戳单位不匹配 → 过期校验完全失效
```lua
if(tonumber(redis.call('time')[1]) > tonumber(redis.call('HGET', _k1, 'issueEndTime'))) then
```
- `redis.call('time')` 返回 `[秒, 微秒]`，`[1]` 是**秒**（≈1.79e9）
- 但 `cacheCouponInfo` 存的是 **`DateUtils.toEpochMilli(...)` 毫秒**（≈1.79e12，2026-09-28 实测 Redis 里就是 `1798732799000`）
- `1.79e9 > 1.79e12` **恒为 false** → 这个校验**永远不触发**，已过期/未开始的券也能兑换
- **修法**：`tonumber(redis.call('time')[1]) * 1000`，或 `now[1]*1000 + math.floor(now[2]/1000)`

### ⚠️ 其他问题
1. **限领超限不回滚**：`HINCRBY _k2 ARGV[3] 1` 已生效才 `return "5"` → 建议 return 前加 `HINCRBY _k2 ARGV[3] -1`
2. **key 前缀硬编码在脚本里**（`"prs:coupon:" .. cid`）→ 与 Java 常量重复，改一处漏一处就出问题；更好做法是由 ARGV 传入前缀
3. **Redis Cluster 不兼容**：脚本里动态拼接 key（`_k1`/`_k2`）+ 操作多个不同 key，Cluster 要求所有 key 同 slot → 直连报错。本项目没上集群，暂不影响，但值得知道
4. `tonumber(HGET ...)` 若 field 不存在会得到 nil → nil 参与比较会报错（低概率，`cacheCouponInfo` 保证 4 字段都在）

### ★ 为什么 LUA 版**不需要分布式锁**（关键收益，面试点）
脚本在 Redis 里**原子执行**（执行期间不插入其他命令）⇒ "判断是否已兑换"和"占位"之间不可能被插队
⇒ 不需要 Java 版那套"先 SETBIT 占位、失败再释放"的补偿逻辑，也**不需要加分布式锁**。
**次要收益**：Java 版一次兑换要 4~6 次 Redis 往返（GETBIT / ZRANGEBYSCORE / HGETALL / HINCRBY / SETBIT），
LUA 版**压成 1 次**。这正是讲义 3.2.1 说的"每次交互都是一次网络请求，并发高时网络拥堵"。

## day11 3.2 文档脚本复核（3.3.5 `receive_coupon.lua` + 3.3.6 Java 调用）

文档正文的 `receive_coupon.lua`（用户贴的 `exchange_coupon.lua` 与 3.3.6 的 Java 调用签名完全对应，确认是课件原文）：

```lua

```
KEYS[1]=`prs:coupon:{id}`、KEYS[2]=`prs:user:coupon:{id}`、ARGV[1]=userId；
Java 侧 `RECEIVE_COUPON_ERROR_MSG[result-1]`（已核对：1活动未开始/2库存不足/3活动已经结束/4领取次数过多）。

### 🔴 真 BUG（两个脚本都有）：时间戳单位不匹配 → 活动结束校验**恒不生效**
`redis.call('time')[1]` 是**秒**（≈1.79e9），缓存 `issueEndTime` 是 `DateUtils.toEpochMilli` 的**毫秒**（≈1.79e12）
→ `秒 > 毫秒` 恒 false → 已过期的券也照领。修法：`tonumber(redis.call('time')[1]) * 1000`

### 🔴 真实缺陷：发 MQ 失败后**兑换码已作废**（3.3.6 Java 侧无 try-catch）
Lua 在成功路径末尾 `SETBIT` 标记已用 → Java 侧拿到 cid → `mqHelper.send(...)`。
**如果 `send` 抛异常，码已被标记、消息却没发出去 → 码永久作废 + 用户没拿到券**，且不可逆。
**修法（注意范围）**：
```java
long r = NumberUtils.parseLong(result);
if (r < 10) { throw ...; }        // 脚本失败 → 脚本没 SETBIT → 不能释放（否则会清掉别人的标记！）
try {
    mqHelper.send(...);
} catch (Exception e) {
    codeService.updateExchangeMark(serialNum, false);   // ★ 只有脚本成功（位是自己占的）才释放
    throw e;
}
```
**关键洞察**：Lua 版把 `SETBIT` 放在**最后** ⇒ Java 侧无法区分"位是我占的"还是"别人占的" ⇒
**释放必须严格限定在"脚本成功之后"**。这也是 Java 版（先 SETBIT 占位、失败释放）在语义上更清晰的地方。

### ⚠️ 其他（非 bug）
1. 限领超限不回滚（`return 4` 前建议加 `hincrby KEYS[2] ARGV[1] -1`）
2. `exists==0` 的文案是"活动未开始"，但暂停/已删除也会走到 → 文案不准（轻微）
3. 两脚本返回风格不一致：receive 用 `0` 表成功 + `Long`；exchange 用**券id**表成功 + `String`（Java 侧靠 `r < 10` 区分）
4. Cluster：KEYS[1]/KEYS[2] 不同 slot；exchange 脚本还动态拼 key（`"prs:coupon:" .. cid`）→ Cluster 直接报错。项目未上集群，暂不影响

### ✅ 文档写对的地方（值得肯定）
- 用 `exists` 判券在不在，**省掉了 status 字段**
- **库存"先读判断、最后扣"—— 在 Lua 里是正确且更简洁的**（原子性保证判断有效，且库存不足时不用回滚）；这比我 9-28 在 Java 版里纠结的"原子扣减 + 回滚"更清爽
- 校验顺序 = 券存在 → 库存 → 时间 → 限领 → 扣库存 ⇒ **先校资格、后占资源**

- key 都通过 `KEYS` 传入（不像 exchange 脚本那样硬编码前缀）

## 3.2 脚本用到的 Redis 命令与数据类型（给用户讲清了）

**4 个数据类型**：String（`coupon:code:serial` 计数器）、Hash（`prs:coupon:{id}` / `prs:user:coupon:{id}`）、
ZSet（`coupon:code:range`）、**BitMap（`coupon:code:map` —— 注意它不是独立类型，本质是 String 的位操作！）**

**7 个命令**：
| 命令 | 作用 | 返回 | 脚本里的用途 |
|---|---|---|---|
| `EXISTS key` | 判断 key 存在 | 存在的个数 | 券缓存在不在（不在=没在发放） |
| `HGET key field` | 取 Hash 字段 | 值；不存在返回 **nil** | 取 totalNum / issueEndTime / userLimit |
| `TIME` | 服务器时间 | **`[秒, 微秒]`** | `time()[1]` 拿秒 ← **bug 源头**（缓存是毫秒） |
| `HINCRBY key field n` | Hash 字段**原子**自增 | 自增后的新值 | 限领 +1、扣库存 −1；key/field 不存在按 0 处理并自动创建 |
| `GETBIT key offset` | 取某一位 | 0/1 | 判码是否已兑换 |
| `SETBIT key offset v` | 置某一位 | **该位旧值** ← 精髓 | 标记已兑换 |
| `ZRANGEBYSCORE key min max [LIMIT o c]` | 按 score 升序取区间成员 | 成员数组 | 反查券（闭区间、score 是 double） |

**★ 三个"下标起点"不一致，极易混**：
| 东西 | 起点 |
|---|---|
| Lua 数组（KEYS/ARGV） | **1** |
| BitMap 的 bit offset | **0** |
| Java 数组 | **0** |

**★ 两个值得记住的语义**：
- `SETBIT` 返回**旧值** → 一次调用同时完成"判断 + 占位"（Java 版限领/兑换就靠它）
- `HINCRBY` **没有上限保护**，能扣成负数 → 所以脚本必须先 `HGET totalNum` 判断（Lua 原子性让"先读后扣"变得安全）

## day12 2.2「定义接口」代码分析（用户："优惠卷智能推荐这个接口的代码你仔细读一读给我分析一下"）

**接口**：`POST /user-coupons/available`
入参 `List<OrderCourseDTO>`；返回 `List<CouponDiscountDTO>`。
**分层**：新建 `IDiscountService`（不塞进 `IUserCouponService`，因为后者已臃肿 → 单一职责）。
Controller 注入两个 service（`IUserCouponService` + `IDiscountService`）。

**完整流程（2.7 的实现）**：
1. `userCouponMapper.queryMyCoupons(UserContext.getUser())` 查我的券（**userId 从上下文取，不放进参** → 防查别人的券）
2. **初筛**：`totalAmount = Σ price`，用 `DiscountStrategy.getDiscount(type).canUse(totalAmount, c)` 过滤
3. **细筛**：`findAvailableCoupon(availableCoupons, orderCourses)` → `Map<Coupon, List<OrderCourseDTO>>`（每张券能用在订单里哪些课程上，用 `cateId` 匹配 `coupon_scope`）
4. **全排列**：`PermuteUtil.permute(coupons)` + **补单券方案** `List.of(c)`
5. **并发算明细**：`CompletableFuture.supplyAsync(..., discountSolutionExecutor)` + `thenAccept(dto -> {list.add(dto); latch.countDown();})` + `latch.await(1, SECONDS)`
6. `findBestSolution(list)`

**★ 最优解算法（两个 Map + 求交集）**：
- `moreDiscountMap`: key = **把券id排序后拼接成字符串**（"1,2,3"），value = 该组合下优惠最高的方案
  → 排序是为了让 `[1,2,3]` 和 `[2,1,3]` 得到同一个 key（"用券相同，不关心顺序"）
- `lessCouponMap`: key = 优惠金额，value = 该金额下用券最少的方案
- 最后 `CollUtils.intersection(两个map.values())` → 按 discountAmount 降序返回

### 🔴 发现 3 个真实隐患（要讲给用户）

**① `thenAccept` 在任务异常时不执行 → `countDown` 漏调 → latch 永远归不了零**
`supplyAsync(() -> calculateSolutionDiscount(...))` 若抛异常，future 异常完成，
**`thenAccept` 不会执行** → 既不加结果也不 countDown → `latch.await(1s)` 必然等到超时。
→ 应该用 **`whenComplete`**（无论成功失败都执行）或 `handle`。
（一个方案失败就拖慢整个接口 1 秒，且结果集缺项。）

**② `latch.await(1, TimeUnit.SECONDS)` 写死 1 秒，且忽略返回值（boolean）**
方案多/算得慢时 1 秒不够 → 结果不全 → `findBestSolution` 基于残缺数据选出"并非最优"的方案。
而且 await 超时后子线程**还在往 list 里 add**，此时主线程在 `findBestSolution` 里遍历同一个
`Collections.synchronizedList` → **有 ConcurrentModificationException 风险**。
→ 更好的做法：`latch.await()`（不限时，或长超时）+ 判断返回值 + 只在全部完成后遍历。

**③ `DiscountStrategy.getDiscount(type)` 可能返回 null，讲义直接链式调 `.canUse()`**
`EnumMap.get(null)` 不抛异常而是返回 null，但紧接着的 `.canUse(...)` 会 **NPE**。
（券的 discountType 若为 null 或未注册的类型就会触发。`Coupon` 的该字段是 `DiscountType` 枚举，
正常不会 null，但边界数据会炸。）

### ⚠️ 一个值得思考的设计问题（未下结论）
`PermuteUtil.permute(list)` 生成的是 **n! 个「用全部 n 张券」的排列**，
**不包含「只用其中 k 张」的子集**（代码只额外补了单券方案）。
→ 所以中间的"用 2 张 / 3 张"组合**没有被枚举**。
这是否够用，取决于 2.5.2 的**券叠加规则**（若券能自由叠加则用全部一定最优，够用；
若存在互斥或需要比较"用券数"，则不够）—— **待读 2.5 后确认，不擅自判定为 bug。**
