```java
public void writeOffCoupon(List<Long> userCouponIds) {
    List<UserCoupon> userCoupons = userCouponMapper.selectList(lambdaQuery().in(UserCoupon::getId, userCouponIds));

            userCouponMapper.updateById(userCoupon);     // ⑤ 循环里逐条 update；⑥ 传整个对象

```

### 🔴 致命问题：有效期判断**写反了** → 功能静默失效
```java
userCoupon.getTermEndTime().isBefore(LocalDateTime.now())
//                         ↑ "结束时间早于现在" = 【已经过期】
```
**现在的逻辑 = 「已过期的券才核销」** ❌；应该是「还在**有效期区间内**才核销」。
**讲义写法**（起止都校验）：
```java
LocalDateTime now = LocalDateTime.now();
return !now.isBefore(coupon.getTermBeginTime()) && !now.isAfter(coupon.getTermEndTime());
```
**后果**：正常下单核销一张未过期的券 → 条件不成立 → **if 进不去 → 券状态一点没变**，
但接口返回 200（void 无异常）⇒ **用户下了单、券还是"未使用"，下次还能再用 → 资损**。
★ **"静默失效"是最危险的一类 bug：不报错，但功能没生效。**
（*根因：`isBefore` / `isAfter` 的方向感 —— 判"在有效期内"要用"不早于开始 && 不晚于结束"*）

### 🔴 其余 3 个缺口
1. **缺 `@Transactional`** —— 批量循环 `updateById`，中途失败会"部分核销"（讲义有注解）
2. **完全没更新 `coupon.used_num`** —— 讲义最后有 `couponMapper.incrUsedNum(couponIds, 1)`；
   不更新 ⇒ 券的"已使用数量"永远是 0。
   ⚠️ **`CouponMapper.incrUsedNum` 全项目还没有**（`CouponMapper` 目前只有 `incrIssueNum`，
   是 `@Update` 注解写的）→ 需要自己加，可照抄 `incrIssueNum` 的写法。
3. **`getStatus().equals(...)` NPE 风险** —— 对象在前，status 为 null 就炸；
   **讲义用枚举在前**：`UserCouponStatus.UNUSED != coupon.getStatus()` ✅
   （和 `Boolean.TRUE.equals(...)` 是同一个套路）

### ⚠️ 4 个可改进
- 循环里逐条 `updateById` → **N 次 SQL**；讲义用 **`updateBatchById(list)`**（一次批量）
- `updateById(userCoupon)` 传整个对象 → 会更新所有非 null 字段（多余）；
  讲义 new 一个空对象只 `setId` + `setStatus`（只更新要改的两列）
- `userCouponMapper.selectList(lambdaQuery()...)` 写法绕 → 直接用 `listByIds(userCouponIds)`（讲义就是）
- `getTermEndTime()` 未判空（讲义同样没判，属共同隐患）

### 讲义 3.2.2 的正确结构（对照）

```java
public void writeOffCoupon(List<Long> userCouponIds) {

    if (CollUtils.isEmpty(userCoupons)) return;

        .filter(coupon -> {

                         x.setStatus(UserCouponStatus.USED); return x; })
        .collect(Collectors.toList());
    updateBatchById(list);
    List<Long> couponIds = userCoupons.stream().map(UserCoupon::getCouponId).collect(Collectors.toList());
    couponMapper.incrUsedNum(couponIds, 1);
}
```

### ★★ 核心教学点：「过期」决定的是【退成什么状态】，不是【退不退】
| | 哪些券要退 | 退成什么状态 |
|---|---|---|
| ❌ 用户写法 | `USED && 未过期`（**过期就不退**） | 一律 `UNUSED` |
| ✅ 正确 | **`USED` 都要退**（跟过没过期无关） | 过期 → `EXPIRED`；未过期 → `UNUSED` |

**同一个条件（是否过期），放进 `if` 里和放进三目里，语义完全不同** —— 这是这次 bug 的根因。
（业务后果：过期券保持 `USED` → 用户在"我的优惠券"里看到"已使用"而非"已过期"；且 `coupon.used_num` 统计偏高。）

## ★★ 答疑：讲义为什么用批量 `incrUsedNum(couponIds, -1)`

已确认讲义签名：**`int incrUsedNum(@Param("couponIds") List<Long> couponIds, @Param("increment") int increment)`**
- 核销（3.2.2）用 `incrUsedNum(couponIds, 1)`
- 退券（3.3.2）用 `incrUsedNum(couponIds, -1)`

### 核心原因：**coupon 这边的"批量"是真·一条 SQL**
```
user_coupon（改状态）：每行 status 值【可能不同】（有的 EXPIRED / 有的 UNUSED）
   ⇒ 没法用一条 SQL 表达 ⇒ 只能 updateBatchById（N 条 SQL 打包，省网络往返）

coupon（改 used_num）：★ 每一行都是同一个操作 used_num = used_num + #{increment}
   ⇒ 完全可以合并成【一条 SQL】：
      UPDATE coupon SET used_num = used_num - 1 WHERE id IN (1,2,3)
   ⇒ 真正的一次往返 + 数据库内部批量
```
**这就是和 `updateBatchById` 的本质区别** —— 那边是"打包 N 条"，这边是"只有 1 条"。

### 第二个原因：一个方法两用
`increment` 参数化 ⇒ 核销传 `1`、退券传 `-1`，**不用写 incr/decr 两个方法**。
（用户写的是两个单条方法 `incrUsedNum(couponId)` / `decrUsedNum(couponId)`；取舍：单一方法 vs 语义清晰。）

### ⚠️ 更正我上一版的判断（"逐个更安全"是过度保守）
我曾担心 `WHERE id IN (100,100,100)` 因 **IN 的集合语义只命中一行** ⇒ 少减。
**但在真实链路下不会重复**：`order.couponIds` ← `discount.getIds()` ← `availableCouponMap.keySet()` 的 creater，
而 **`availableCouponMap` 的 key 是 `Coupon` 对象 ⇒ 同一张券一个订单里只会出现一次** ✅
⇒ **讲义的批量是安全的**，改用批量更好（更彻底 + 和讲义一致）。
（这个"为什么不会重复"的推导依赖 `Map<Coupon,...>` 的 key 唯一性，值得记住。）

**★ 由此得到一个通用判断**：
- 需要更新的**每行值相同**（同一个增量）→ 能合并成**一条 SQL**（`IN` + `SET x = x + n`）
- 需要更新的**每行值不同**（不同 status）→ 只能"批处理打包"（`updateBatchById`）或写 `CASE WHEN`

## 答疑：既然用户在页面上"选好了"方案（下拉框），为什么服务端还要再筛一遍？

用户看到订单确认页的下拉框「叠加4券：【优惠108元】」，问"为什么还要筛选，不是从这里面选吗"。

**答（4 条理由）**：
1. **不能信任前端参数** —— `userCouponIds` 是外部传进来的，可伪造/篡改（换成别人的用户券id、
   换成不在方案里的券）⇒ 服务端必须自己验
2. **时间差** —— `/available` 是用户**打开页面时**算的；`/discount` 是**点提交时**调的，
   中间隔了几十秒到几十分钟 ⇒ 期间某张券可能**已被用掉/已过期**、商品可能下架改价 ⇒ 必须重验
3. **★★ 最关键：`/discount` 的产出不止"再筛一遍"，而是 `discountDetail`** ——
   `/available` 返回的 `CouponDiscountDTO` **只有 ids/rules/discountAmount，没有明细**；
   `/discount` 才有 `discountDetail`（每件商品优惠多少）。
   **下单时必须把明细落库**（算每件商品实付金额 → 将来部分退款按实付退，面试题 4.5）
   ⇒ 这个数据**不能依赖前端传**，必须服务端现算
4. **职责不同**：`/available` = **推荐**（从所有券里挑出多个方案供选）；`/discount` = **验算**（对选定的方案重新校验 + 出明细）

**具体筛两个条件**：
- `uc.status = UNUSED`（券状态）
- `findAvailableCoupons(coupons, courseList)`（券的适用范围 + 在**这张订单**上够不够门槛）

**完整链路**：
```
① 打开订单确认页 → POST /available → [{ids,rules,discountAmount}, ...] → 前端渲染下拉框
② 用户选中「叠加4券：优惠108元」→ 前端拿到该方案的 ids
③ 点提交 → 交易服务调 POST /discount {userCouponIds, courseList}
        → 服务端重新校验 + 算出 discountDetail
        → 用返回的 discountAmount + discountDetail 创建订单、核销券
```
**类比**：`/available` = 超市货架上帮你挑券；`/discount` = 收银员结账时再核一遍（券还能用吗？有效期到了吗？）才算钱。

### 🔴 漏项 C：**没定义 `queryCouponByUserCouponIds`** → 引发两个问题
- **没过滤 `status = UNUSED`**（讲义 SQL 里 `AND uc.status = #{status}`）⇒ 已用/过期的券也能算优惠
- **N+1**：循环里 `couponMapper.selectById(...)` 逐条查 ⇒ 应一次多表联查（讲义的新 SQL 正是为此）
- Mapper 和 XML 里**都没有**这个方法（还没写）

### ⚠️ 顺序不可控
`new ArrayList<>(availableCouponMap.keySet())` —— HashMap 的顺序由 hashCode/容量决定，
**不可读、不可控**；而 `calculateSolutionDiscount` 的**结果依赖顺序**。
讲义传的是 `coupons`（List）。
（⚠️ 客观说：同一批 key 在同一 JVM 下顺序通常是稳定的，且讲义的 `IN` 查询顺序同样不保证 ——
所以这是**两者的共同问题**；建议**显式排序**（如按券id）来保证幂等。）
