## ★ 为什么 day10 版本「需要」DB 查一遍限领，day11 2.4 又必须删掉

**day10 需要它，因为两个条件同时成立**：
1. **DB 是唯一数据源** —— 那时候没有 Redis 计数器，"这个用户领了几张"只存在 `user_coupon` 表里，不查 DB 就没法判断
2. **有悲观锁把「查 → 判断 → 插入」串行化** —— day10 是 `@Transactional` + 锁 + 同步调用，三步在同一事务内完成。锁保证线程B必须等A提交完才能读到 count，所以非原子的三步是安全的

**day11 2.4 必须删它，因为这两个条件都不成立了**：
1. Redis 的 `HINCRBY user:coupon:{couponId}` 成了**新的原子权威**（一条命令完成"读+自增"），DB 退化成第二套权威，两边不一致时没有裁决标准
2. **落库挪到 MQ 消费者，消费者身上没有任何锁** → 「查 → 判断 → 插入」重新变成非原子操作。同一用户两条消息被两个消费者线程同时处理 → 都读到 count=0 → 都通过 → **限领失效**
3. 附带：DB count 反映"落库进度"，Redis 计数反映"受理进度"，两者有时间差（MQ 队列积压时差得很远）→ DB 可能给出**假阳性** → 消息消费失败进重试队列无限重试，而 Redis 计数已被占用 → 用户看到"领取成功"但券永不到账

**★ 关键区别：为什么库存的 DB 兜底（`incrIssueNum`）能留，限领的不能留**
- **库存兜底 = 原子条件更新**：`UPDATE coupon SET issue_num = issue_num + 1 WHERE id = ? AND issue_num < total_num` —— "判断"和"更新"在**同一条 SQL 里**完成，DB 保证原子 → 永远不会误判，所以能当兜底（双保险）
- **限领校验 = 先查后判断再插入**（三条语句）→ 非原子 → 在无锁环境下必然漏判 → 不能当兜底。它的原子替代品就是 Redis 的 `HINCRBY`

**一句话**：兜底必须是「原子的」，非原子的兜底 = 假保险。

## ★ 核心概念：为什么库存要校验两次、限领不该校验两次（Check-Then-Act）

用户反复问到"前面校验过了为什么后面还要再校验"。统一答案 = **Check-Then-Act 竞态**：

**第 1 层「快速失败」**：读一个快照判断（`issueNum >= totalNum`）→ 挡掉绝大多数请求，减少进入写流程的量。
**第 2 层「原子兜底」**：在**写入的那一刻**用原子操作再判一次（`UPDATE ... WHERE issue_num < total_num` / `HINCRBY`）。

**为什么必须有第 2 层**：第 1 层的判断结果在你用它的时候**已经过期了**。两个并发请求会读到同一个快照（都读到 9，totalNum=10），于是**第 1 层谁也拦不住**。真正的裁决只发生在写入那一刻。
→ 用户 day08 的注释自己就写明了这点：「这里只是快速失败……真正的并发保护在 incrIssueNum 的 WHERE 条件里，因为这一步查出来的 issueNum 在并发下可能已经过期了」

**★ 库存能有两层、限领不能有两层的原因**：
- 库存：第 2 层有「原子条件更新」这个手段 → 可靠兜底
- 限领：第 2 层做不到一条 SQL（要先查再插）→ 非原子 → **当不了兜底**。而第 1 层（Redis `HINCRBY`）**本身已经是原子的**，它自己就是"第 2 层"，不需要别人兜它
- 所以 `checkAndCreateUserCoupon` 里的 DB `count()` 限领校验要删：它既拦不住（非原子），又会误判（DB count 滞后于 Redis 计数 → 假阳性 → 消费失败进重试队列无限重试）

**一句话**：兜底必须是原子的；非原子的兜底不是保险，是假保险。

## ★ 为什么限领校验不能写在 receiveCoupon 里（旧版）

**用户追问**："为什么不直接在 receiveCoupon 里判断是否超额领取？"

**核心答**：**校验放在哪个方法，跟着它的数据源和"原子单元"走。**
- 限领的判断依据是 `user_coupon` 表的 `count(*)`，而"写入 user_coupon"这一步在 `checkAndCreateUserCoupon` 里
- 「查 count → 判断 → 插入」**是一个原子单元**，必须和"插入"待在一起、被同一把锁/事务罩住
- 硬拆到两个方法 → 「查」和「插」被方法边界切开 → 并发下两个线程照样都读到 0 → 漏判

**次要原因**：
1. 两条领券路径（`receiveCoupon` 手动 / `exchangeCoupon` 兑换码）都要做限领校验 → 抽公共方法，只有一份实现
2. 更要紧的是：day10/day11 后续所有并发改造（乐观锁、加锁、事务边界）全落在这段逻辑上，**有两份必然改漏一处**

**★ 反面印证（很漂亮的一点）**：2.4 改造后，限领校验**确实搬进 `receiveCoupon` 了** —— 因为它换了数据源：
- 旧版：查 `user_coupon` 表 → 数据只有落库后才有 → 必须待在落库阶段
- 新版：改查 Redis 计数 → 计数在 `receiveCoupon` 里就写了 → 校验自然跟着搬过去

**即：原来的拆分位置，正好就是同步/异步的边界。** 而这个边界的划分依据 = 校验的数据源在哪。

## ★ 为什么旧版「不能」在 receiveCoupon 校验、新版「必须」在 receiveCoupon 校验

**两个版本受两个方向相反的约束 —— 这才是问题真正的答案。**

**旧版：不能放（原子性约束）**
- 限领判断依赖 `user_coupon` 表的 `count(*)`，而写 `user_coupon` 就在 `checkAndCreateUserCoupon`
- 「查 count → 判断 → 插入」是原子单元，拆开就被方法边界切开 → 并发下漏判

**新版：必须放（★ MQ 承诺线约束）**
- 2.4 之后落库挪到 MQ 后面。**发 MQ 是一条不可回退的承诺线**：消息发出 = 承诺"这个用户一定会拿到券"
- 所以**所有可能失败的资格判断都必须在发消息之前做完**
- 若把校验留在消费者里：① 用户端早已返回"领取成功"，却永远不知道没领到；② 校验失败只能靠抛异常 → 消息进重试队列**无限重试**、死信堆积；③ 前面扣掉的 Redis 库存被白白占用
- 结论：`receiveCoupon` 是同步受理阶段 = 校验的最后一道关口

**约束为什么反转**：**数据源从 DB 换成了 Redis**。
- 旧版校验依赖"插入的结果" → 离不开插入 → 被绑在 `checkAndCreateUserCoupon`
- 新版校验依赖 Redis 计数器 → 与插入解耦 → 可以（且必须）提前到 `receiveCoupon`

**一句话**：旧版"校验离不开写入"，新版"校验必须早于承诺"。约束方向相反，落点自然相反。

### 缺口：`beginIssueBatch` 没有写缓存（P0，讲义明确留的作业）

**讲义 2.2.3 原文 callout**：
> 对于延时发放的优惠券，将来需要编写定时任务，扫描发放时间已经到了的优惠券。修改状态为发放中，**同时添加优惠券缓存**。这部分功能留给大家实现。

**我们的代码**：`CouponServiceImpl.beginIssueBatch()` 只做了批量 UPDATE（UN_ISSUE → ISSUING），**没有写缓存**。

**后果（严重）**：延时发放的券被定时任务改成 ISSUING 后，Redis 里没有它的缓存 → 用户点领取时 `queryCouponByCache` 返回 null → **一律抛"优惠券不存在"**。这不是"优化没做"，是**这条业务线完全不通**。

**而且是活的**：`CouponTask.checkIssueStatus()`（`@Scheduled(cron = "0 * * * * ?")`，每分钟一次）已经在调它。

**修复思路**：批量 UPDATE 不把数据捞进内存，无法逐条写缓存。需要改成：
1. 先查出"即将开始发放"的券 id 列表（`status = UN_ISSUE AND issue_begin_time <= now`）
2. 再执行批量 UPDATE
3. 遍历列表，逐条 `cacheCouponInfo`（注意 `issueBeginTime` 要用刚写入的时间）
或：先 UPDATE 再按 `status = ISSUING AND issue_begin_time <= now` 反查 —— 但会误捞已发放的券，不可靠。

### 次要：`endIssueBatch` 没有删缓存（低优先级）

讲义 2.2.4 说「优惠券暂停发放，**或者优惠券过期时**，应该移除优惠券缓存」，但只给了暂停的代码，过期那段没给。
- 当前不删也**不影响正确性**：`receiveCoupon` 读得到缓存，但时间校验 `now.isAfter(issueEndTime)` 会拦住
- 唯一代价：缓存泄漏（Redis 里一直留着过期券的 Hash）

### 🐛 BUG：限领校验失败时没有回滚库存（库存泄漏）

**根因：我把讲义里的执行顺序改坏了。**

- **讲义顺序**：校验库存（只读判断）→ **校验限领** → 扣库存 → 发 MQ
- **我改成的顺序**：**扣库存**（原子判断）→ 校验限领 → 发 MQ

于是限领失败分支里只回滚了 `userKey`，**没回滚 `couponKey` 的 totalNum**：
```java
Long count = increment(userKey, userId.toString(), 1L);
if (count > coupon.getUserLimit()) {
    increment(userKey, userId.toString(), -1L);   // ← 只回滚了限领
    throw new BadRequestException("超出领取数量");  // ← 库存的 -1 没还回去
}
```

**后果**：用户每被限领拦一次，就白白消耗一个库存名额，永不归还。
限领失败是**高频路径**（用户重复点击），所以危害被放大 —— 同一人点 100 次，券直接少发 100 张。

**修复方案**（保留我的"原子扣库存"，但把顺序调回来，并在库存失败时回滚限领）：
```java
// 3.先校验每人限领（资格失败不该碰公共库存）
Long userId = UserContext.getUser();
String userKey = USER_COUPON_CACHE_KEY_PREFIX + couponId;
Long count = increment(userKey, userId.toString(), 1L);
if (count > coupon.getUserLimit()) {
    increment(userKey, userId.toString(), -1L);
    throw new BadRequestException("超出领取数量");
}
// 4.再扣库存（失败要把限领计数也还回去）
String couponKey = COUPON_CACHE_KEY_PREFIX + couponId;
Long left = increment(couponKey, "totalNum", -1L);
if (left == null || left < 0) {
    increment(couponKey, "totalNum", 1L);
    increment(userKey, userId.toString(), -1L);      // ★ 别忘了这句
    throw new BadRequestException("优惠券库存不足");
}
```
**原则：先校资格、后占资源。** 任何一处的扣减失败，都要把**另一处**也回滚。

## 库存泄漏 BUG 修复（代码已改完并编译通过，实测待虚拟机开机）

**改法：把 `receiveCoupon` 的执行顺序改回「先校资格、后占资源」**

```java
// 3.校验每人限领数量（先校资格）
Long userId = UserContext.getUser();
String userKey = PromotionConstants.USER_COUPON_CACHE_KEY_PREFIX + couponId;
Long count = redisTemplate.opsForHash().increment(userKey, userId.toString(), 1L);
if (count > coupon.getUserLimit()) {
    redisTemplate.opsForHash().increment(userKey, userId.toString(), -1L);
    throw new BadRequestException("超出领取数量");
}
// 4.扣减库存（失败要成对回滚）
String couponKey = PromotionConstants.COUPON_CACHE_KEY_PREFIX + couponId;
Long left = redisTemplate.opsForHash().increment(couponKey, "totalNum", -1L);
if (left == null || left < 0) {
    redisTemplate.opsForHash().increment(couponKey, "totalNum", 1L);
    redisTemplate.opsForHash().increment(userKey, userId.toString(), -1L);   // ★ 新增
    throw new BadRequestException("优惠券库存不足");
}
```

## ✅ 补齐 `beginIssueBatch` 写缓存（讲义留的作业）— 已实现并实测通过

**改动**：`CouponServiceImpl.beginIssueBatch()` 从"一条批量 UPDATE"改成"先查 → 按 id 改状态 → 逐条写缓存"。

```java
public void beginIssueBatch() {
    // 1.查出到达开始时间、状态还是 UN_ISSUE 的券
    List<Coupon> coupons = lambdaQuery()
            .eq(Coupon::getStatus, CouponStatus.UN_ISSUE)
            .le(Coupon::getIssueBeginTime, LocalDateTime.now())
            .list();
    if (CollUtils.isEmpty(coupons)) return;
    // 2.按 id 批量改状态（★ 不用原条件重查，保证"改了的都写了缓存"）
    List<Long> ids = coupons.stream().map(Coupon::getId).collect(Collectors.toList());
    lambdaUpdate().set(Coupon::getStatus, CouponStatus.ISSUING)
                  .in(Coupon::getId, ids).update();
    // 3.逐条写缓存
    for (Coupon coupon : coupons) cacheCouponInfo(coupon);
}
```

**三个设计要点（都写进注释了）**：
1. **查询必须在 UPDATE 之前** —— UPDATE 会把状态改成 ISSUING，之后再按 `issue_begin_time` 反查会把"早就发放完、只差没到结束时间"的老券也捞出来，脏数据被重新写进缓存
2. **按 `in(id, ids)` 更新，不重写原条件** —— 保证"被改状态的行"就是"查出来的那批"，否则两次查询之间若有新券满足条件，会出现"改了状态却漏了缓存"的券，且它下一轮也不会再被选中（状态已是 ISSUING）→ **永久漏网**
3. **时间用券上排期的原值，不覆盖成 now** —— 与 `beginIssue`（立刻发放要 `setIssueBeginTime(now)`）不同，延时发放的时间是运营排好的

## day11 3.1 异步兑换码领券 —— 现有代码盘点与机制澄清

**★ 3.1 缓存的不是「兑换码数据」，而是「券id → 该券兑换码号段的最大序列号」这个 ZSet**

### ★ 关于 `exchangeCoupon` 的锁：虎哥自己改过两次

查 4 个参考 commit 发现演变：

**★ 我对这个锁的必要性存疑**（做的时候要讨论）：
- "一个码只能兑一次" 已由 SETBIT 保证
- "限领不超" 已由 HINCRBY 保证
