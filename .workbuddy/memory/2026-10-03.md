## 答疑：MyBatis-Plus 是不是只能做单表查询？

用户问"mybatis-plus 是不是只能实现单表查询" → **不是**。要从项目里找证据说明。

**关键区分（这是答案的核心）**：
- **MP 的「通用 CRUD 方法」**（`selectById` / `selectList(wrapper)` / `updateById` / `selectPage` …）→ **确实只能单表**。
  它们靠"实体 ↔ 表"一对一的 `@TableName` 映射自动生成 SQL，多表联查需要 join 条件、字段别名、结果映射，MP 无从得知。
- **Mapper 接口 / XML 本身不限于单表** → 随便声明方法、写任意 SQL。

**★ 项目里的现成实例**：`tj-user/.../UserDetailMapper`（`extends BaseMapper<UserDetail>`，是 MP 的 Mapper）
```java
UserDetail queryById(Long userId);
List<UserDetail> queryByIds(List<Long> ids);
Page<UserDetail> queryByPage(Page<UserDetail> p, @Param("ew") QueryWrapper<UserDetail> wrapper);
```
```sql
SELECT u.cell_phone, ..., ud.type, ud.name, ...
FROM `user` u LEFT JOIN user_detail ud ON u.id = ud.id     -- 两张表
WHERE u.id = #{userId}
```
（项目中含 `JOIN` 的 mapper XML：`QuestionBizMapper.xml`(tj-exam)、`UserDetailMapper.xml`(tj-user)）

**★ 最佳实践 `queryByPage`：多表联查 + MP 条件构造器**
```sql
SELECT ... FROM `user` u LEFT JOIN user_detail ud ON u.id = ud.id
${ew.customSqlSegment}      -- 会替换成 MP 的 Wrapper 生成的 WHERE 子句
```
```java
Page<UserDetail> queryByPage(Page<UserDetail> p, @Param("ew") QueryWrapper<UserDetail> wrapper);
```
→ 表连接自己写，WHERE 交给 MP 动态拼，分页由 MP 分页插件处理（传 `Page` 参数）。

**MP 下写多表查询的方式**：自定义 XML（最常用）/ `@Select`等注解（短 SQL）/ `${ew.customSqlSegment}`（多表+动态条件，最佳实践）/ MPJ 社区插件（lambda 风格写 join）。
项目里注解方式很多：`CourseCataSubjectDraftMapper`(5)、`CourseCataSubjectMapper`(4)、`CourseCatalogueDraftMapper`(4) 等。

**回到 day12**：这正是 `queryMyCoupons` 必须手写 SQL 的原因 ——
条件在 `user_coupon`、返回值要 `coupon` 的规则字段 → 两张表 → MP 通用方法做不到。
（Java 侧绕行方案：先查 user_coupon 拿 couponId，再 `selectBatchIds` 查 coupon —— 两次查询 + 内存组装，不如一次联查。）

## 答疑：为什么筛两次？不能直接细筛吗？

用户问"为什么要做两次筛选，不直接进行第二次细筛就是了"。

**答：可以，初筛是「性能优化」而非「功能必需」。**

**核心：两次筛选的成本悬殊**
| | 初筛 | 细筛 |
|---|---|---|
| 查 DB 吗 | ❌ 纯内存（Σ price 一次遍历） | ✅ **每张券一次 `coupon_scope` 查询** |
| 成本 | ~0 | N 次 SQL |

**★ 初筛为什么不会误杀**（数学依据）：
订单总价 **≥** 券范围内课程总价（范围内课程是订单的**子集**）
→ 「全部都不够门槛」⇒「子集更不够」⇒ 初筛淘汰的一定是"注定不可用"的券 ✅
→ 反之 **初筛通过 ≠ 可用**（券可能只覆盖部分课程）⇒ 必须再过细筛

例：订单 Java100(a) + 数学100(b) = 200
- 券A 满150减20 无限定 → 初筛过、细筛过 ✅
- 券B 满150减20 限定 a → 初筛过（200≥150）、**细筛淘汰**（100<150）❌
- 券C 满1000减100 → **初筛就淘汰**，省下查范围表的开销 ✅

### ★★ 发现：细筛目前是 **N+1 查询**（可优化）
讲义 `findAvailableCoupon` 的实现：
```java
for (Coupon coupon : coupons) {
    if (coupon.getSpecific()) {
        // ↓ 循环里逐条查 DB —— 100 张限定范围的券 = 100 次 SQL
        List<CouponScope> scopes = scopeService.lambdaQuery()
                .eq(CouponScope::getCouponId, coupon.getId()).list();
    }
}
```
→ 典型 N+1。**优化方案**：先收集所有 `specific=true` 的 couponId，
一次 `WHERE coupon_id IN (...)` 查回来，在内存里 `groupingBy` 成 `Map<Long, Set<Long>>`（券id → 分类id集合）。
→ 这也**进一步放大了初筛的价值**（券多时能砍掉大量范围查询）。
（用户型项目数据量小，讲义不优化也能接受；但面试问"这段代码怎么优化"就是答这个。）

## 分析：`DiscountStrategy`（策略工厂）

用户要专门分析这个类。

**三个角色（GoF 策略模式）**：
- 策略抽象 = `Discount` 接口
- 具体策略 = `NoThresholdDiscount` / `PriceDiscount` / `PerPriceDiscount` / `RateDiscount`
- **本类 = 「简单工厂」**（注意：严格说不是 GoF 的 Context，Context 角色其实由调用方 `DiscountServiceImpl` 承担）

**不用它的"三宗罪"**（对比 if-else）：
1. **同一段 if-else 会散落多处** —— `canUse` / `calculateDiscount` / `getRule` 各要一份，加一种券要改 3 处
2. **违反开闭原则** —— 新增券类型要动已有代码，漏改风险高
3. 单方法会变得很长（4 种算法挤在一起）

**实现细节的 3 个讲究**：
1. **`EnumMap` 而非 `HashMap`** —— key 是枚举时它内部就是个**数组**（用 ordinal 当下标），无哈希计算/无冲突链表，更快更省
2. **`final static` + 静态块** —— 4 个实现类**无状态**（不存字段），全应用共享 4 个实例即可
3. **手动静态工厂不是 Spring 注入** —— 好处：静态方法可直接调，任何地方都能用（不需要注入）；
   代价：新增券类型**仍要改工厂代码**（开闭原则只做到一半）

**⚠️ 真实坑：`getDiscount` 可能返回 null → 调用方 NPE**
```java
public static Discount getDiscount(DiscountType type) { return strategies.get(type); }
```
- `EnumMap.get(null)` **不抛异常，返回 null**（`isValidKey(null)` 为 false）
- 讲义三处调用都是直接链式 `getDiscount(t).canUse(...)` → 一旦 type 为 null 就 **NPE**
- 正常不会（DB `discount_type` 非空），但**健壮性上应防**（判空或给个空实现）
- 2026-10-02 已记录为讲义代码问题之一

**和 day11 锁组件的类比**：`LockTypeEnum` + 工厂选锁实现、`LockFailStrategy` 选失败策略 —— 同一套思想。
**面试题 4.2 直接答它**：策略模式（接口 + 4 实现）+ 简单工厂（EnumMap 装配）。

```java
public enum LockType {
```

```java
boolean success = properties.lockStrategy().tryLock(rLock, properties);
// @Lock: LockType lockType() default DEFAULT;
//        LockStrategy lockStrategy() default FAIL_AFTER_RETRY_TIMEOUT;
```

## `DiscountStrategy` 深度拆解（第二次讲，用户要更仔细）

**★ 新验证出的 5 个可改进细节**（都是讲义代码的小瑕疵，不影响功能）：
1. **4 个实现类的 `@RequiredArgsConstructor` 完全多余** —— 已验证它们**都没有实例字段**
   （只有 `private static final String RULE_TEMPLATE`，static 不算 required）→
   该注解生成的构造器就是无参构造器，而编译器本来就会生成 → 注解无任何效果，应从模板里删掉
2. **`DiscountStrategy` 没有私有构造器** → 可以被 `new DiscountStrategy()` 无意义地实例化
   （工具类惯例：`private DiscountStrategy() {}`）
3. **类都没有 `final`** → 可被继承（工具类惯例加 `final`）
4. 修饰符顺序写成 `private final static`，惯例是 `private static final`（语义等价，Java 不要求顺序）
5. 字段声明成具体类型 `EnumMap` 而非接口 `Map` → 不利于将来替换实现（无害但不够好）

**`EnumMap` 快的原理 + 诚实的评价**：
- 原理：内部就是个**数组**，用 `enum.ordinal()` 直接当下标 —— 无 hashCode 计算、无扰动、无冲突链表/红黑树
- 量级：`HashMap.get` ≈ 10~20ns，`EnumMap.get` ≈ 1~3ns
- **★ 诚实结论：确实更快，但都是纳秒级，业务代码感知不到。真正的价值在别处**：
  ① 类型安全（key 必须是该枚举）② 不会因 hashCode 实现不当而退化 ③ 内存更省 ④ 遍历按 ordinal 有序
- ⚠️ 不要对用户夸大 EnumMap 的性能优势

**静态初始化块的三个要点**：
- 类加载时执行**一次**，且 JVM 保证在**任何静态方法被调用之前**完成
- **`<clinit>` 由 JVM 保证线程安全**（同一个类只初始化一次）→ 所以这里的组装是天然线程安全的
- `final` 字段必须在静态块里**恰好赋值一次**，否则编译报错

**★ "加一种新券类型要改哪几处"（检验开闭原则的好问题）**：
1. `DiscountType` 加常量（必须在，因为要落 DB）
2. 新建 `XxxDiscount implements Discount`
3. **`DiscountStrategy` 静态块加一行 `put`** ← **最容易漏！**
4. 漏了第 3 步 → `getDiscount` 返回 null → 调用方 NPE
   → **"漏注册"和"返回 null"是同一个问题的两头**（这是我上次说的 null 坑的根因）

**`final` 的语义提醒**：`final` 只锁**引用**，不锁内容 —— `strategies` 是 final，但仍可 `put`（引用没变）。

## 讲义 2.4「细筛」深度分析（`findAvailableCoupon`）

**职责一句话**：把「券列表 + 订单课程」→ 变成 `Map<这张券能用, 能用在哪些课程上>`。

**★ 方法签名里藏着的关键设计**：返回 **`Map<Coupon, List<OrderCourseDTO>>`** 而不是 `List<Coupon>`。
原因：后面 `calculateSolutionDiscount` 算每张券优惠时，需要知道"这张券能用在哪几门课上"（要用这些课的**折后总价**算门槛）。
若只返回 `List<Coupon>`，后面还得**再查一次范围表** → 重复查 DB。
→ 讲义原话：「细筛完成后，建议把每个优惠券及对应的可用课程缓存到一个 Map 中，**避免后期重复查找**」。
→ **即"用返回值传递中间结果"，一次查询两用（筛选 + 建索引）。**

**逐行要点**：
1. `List<OrderCourseDTO> availableCourses = courses;` —— **先默认"全部课程"**，不限范围的券（specific=false）直接用；再按需覆盖。写法简洁
2. `Set<Long> scopeIds = scopes.stream().map(CouponScope::getBizId).collect(toSet())` —— **用 `Set` 而不是 `List`** → `contains` 是 O(1)（否则 filter 里 `contains` 是 O(n)，变成 O(n×m)）✅ **正确的选择**
3. `courses.filter(c -> scopeIds.contains(c.getCateId()))` —— **`OrderCourseDTO.cateId` 对上 `CouponScope.bizId`**，这是"券使用范围"真正落地的地方
4. 保留的是**课程对象**（不是分类id）—— 因为后面要用 `price` 算钱
5. `if (CollUtils.isEmpty(availableCourses)) continue;` —— "没有可用课程 = 券不可用"，直接跳过（不抛异常、不放进 map 让后面判空）✅
6. 判断用的是**范围课程总价**（不是订单总价）—— 这就是细筛 vs 初筛的本质区别

### 🔴 发现的 3 个隐患

**① `if (coupon.getSpecific())` 有自动拆箱 NPE 风险** ❌
`specific` 是 `Boolean` **包装类**，为 null 时 `if (null)` 自动拆箱 → **NPE**。
而**项目里另外 3 处都写了 `Boolean.TRUE.equals(...)`**（`CouponServiceImpl` 73/211/250 行，是我们自己的写法）→ **讲义这里风格不一致且不安全**。
（当前数据不会踩到：`queryMyCoupons` 明确 select 了 `c.specific`，DB 列非空；但边界数据会炸。）

**② N+1 查询** ❌ —— `for` 循环里逐条 `scopeService.lambdaQuery().eq(couponId, ...).list()`，
N 张限定范围的券 = N 次 SQL。**优化**：先收集所有 `specific=true` 的 couponId，
一次 `WHERE coupon_id IN (...)` 查回，内存 `groupingBy` 成 `Map<Long, Set<Long>>`（券id → 分类id集合）。

**③ `DiscountStrategy.getDiscount(...)` 可能返回 null** → `.canUse()` NPE（老问题）。

### ⚠️ 一个"能用但不稳"的写法
用 **`Coupon` 实体对象当 `HashMap` 的 key**。`Coupon` 有 `@Data + @EqualsAndHashCode`，所以能用；
且这里 `get(coupon)` 用的是**同一个对象引用**（都来自 `availableCoupons`），走 `==` 必然命中 → 实际安全。
但**实体是可变的，把它当 Map key 本身是坏习惯**（字段一改 hashCode 就变，key 就找不到了）。
更稳的做法：**用 `couponId` 当 key**（`Map<Long, List<OrderCourseDTO>>`）。

**其他微优化**：`new HashMap<>(coupons.size())` 没算负载因子 0.75（理想是 `n/0.75+1`）→ 可忽略。

## ★★ 讲义 2.5「优惠方案全排列组合 + 计算优惠明细」分析（含一个漂亮的论证）

### 2.5 的思路
券放 List，**下标 [0~N) 的全排列 = 券的使用顺序**；用回溯算法（LeetCode 46）→ `PermuteUtil` 就是干这个的。

### 2.5.1 单张算法（4 步）
① 判断限定范围（找出范围内课程）② 算课程总价 ③ 判断券是否可用 ④ 算优惠金额

### ★★ 2.5.2 券叠加 —— 讲义的例子（务必记住这组数）

```
商品：1(100, a)  2(100, b)  3(100, b)     总价 300
券1：每满 100 减 20，适用 a,b
券2：满 200 减 100，适用 b
券3：满 80 减 20，适用 a

按顺序 券1 → 券2 → 券3：
① 券1：范围全部 → 总价300 ≥ 门槛100 ✅ → 每满100减20×3 = 【减 60】
        明细分摊：商品1、2 各 (100/300)*60 = 20；商品3 = 60-20-20 = 20（最后一个用减法兜底）
        detailMap = {1:20, 2:20, 3:20}
② 券2：范围 b（商品2、3）→ 【总价用折后价 = (100-20)+(100-20) = 160】
        → 门槛 200，160 < 200 ❌ 【不可用，跳过】（本来够门槛的，被券1挤掉了！）
③ 券3：范围 a（商品1）→ 折后价 = 100-20 = 80
        → 门槛 80，80 ≥ 80 ✅（刚好达到）→ 满80减20 = 【减 20】→ 明细 {1:40, 2:20, 3:20}
总优惠 = 60 + 0 + 20 = 【80 元】
```

**★ 若换成 券2 → 券1 → 券3**：券2 先算（b类总价200 ≥ 200）减 100 → 券1 按折后总价200 每满减40 → 券3 减20
→ 总优惠 = 100 + 40 + 20 = **160 元**（是刚才的 2 倍！）
→ **这就是"顺序极其重要"的实证**。

### ★★★ 解答我之前的疑问：为什么只枚举「全排列」就够了，不用枚举「用 k 张」的子集？

**论证（三步）**：
1. **加一张券，总优惠「单调不减」** —— 券算出的优惠额 ≥ 0；若不可用则 `continue` 跳过（不影响已有结果）。
   已生效的券的优惠额已累加进 `dto.discountAmount`，不会因后继券而减少。
2. 任取一个"用子集 T"的方案，把它**接在"剩余券"后面**，就得到一个**全排列**方案 P（T 是 P 的前缀）。
3. 由 1 得 P 的优惠 **≥** T 的优惠 ⇒ **任何子集方案的优惠，都能被某个全排列方案追平或超越** ⇒ **最优解必然落在全排列集合里** ✅

→ **结论：讲义只枚举全排列是「正确」的**，不是缺陷。（单券方案 List.of(c) 在 n=1 时就是排列本身，属于冗余补齐，无害。）
→ **我 2026-10-02 记的"全排列≠全组合，可能不够用"—— 更正：够用。**

### 优惠明细（`calculateDiscountDetails`）的两个要点
1. 按 **价格占比** 分摊：`discount = discountAmount * course.getPrice() / totalAmount`
2. **最后一个商品用减法兜底**：`discount = remainDiscount`（= 总额 − 前面已分摊之和）
   → 因为整数除法**向下取整**，逐个按比例算会累加不足，让最后一个"吃掉余数"保证 `Σ明细 == 总优惠` ✅

用户说的"4.5"= 我上一条消息里的**第四点（为什么只枚举全排列就够）**和**第五点（优惠明细算法）**。

### 四、论证要讲清「前缀」这个关键（第一次讲漏了它）
**疑问**：`PermuteUtil.permute` 只生成"用全部 n 张券"的排列，不生成"用 k 张"的子集，会漏最优解吗？
**答案**：不会。证明三步：
1. **单调性**：`calculateSolutionDiscount` 里券不可用 → `continue`（优惠不变）；可用 → `dto.discountAmount += 券优惠`（只加不减）；已加的优惠不会被后续券撤销。
   ⇒ **在任意方案末尾再接一张券，总优惠 ≥ 原方案**
2. **补券构造**：任取子集方案 T，把"没用到的券"接在 T **后面** → 得到全排列 P（**T 是 P 的前缀**）
3. ⇒ P 优惠 ≥ T 优惠。而 `permute` 生成的是**全部** n! 个排列 ⇒ **必然包含"以 T 为前缀"的那些**
⇒ **任何子集方案的优惠，都能被某个全排列追平或超越** ⇒ 最优解必在全排列里 ✅

**★ 关键细节（第一次没讲）**：不是"所有全排列都 ≥ T"，而是"**至少有一个**（以 T 为前缀的那个）≥ T"。
用 2.5.2 的例子验证：子集 {券2} 单独用 = 100 元；
`[券1,券2,券3]` = 80（**小于 100**）；但 `[券2,券1,券3]` = 160 ≥ 100 ✅ —— 我们取所有排列的最大值，所以拿到 160。

**⚠️ 不成立的前提**：依赖"优惠单调不减"。若将来引入**互斥券**（用A就不能用B）或负数优惠，论证失效。

### 五、优惠明细——用具体数字讲"最后一个兜底"的必要性
```
总优惠 10 元，三件商品 1000 / 1000 / 1001（总价 3001）
三件都按比例算（整数除法向下取整）：
  10*1000/3001 = 3（砍掉 0.33）
  10*1000/3001 = 3
  10*1001/3001 = 3
  合计 = 9 ≠ 10  ❌ 少了 1 元！
兜底后：3 / 3 / (10-3-3)=4  → 合计 10 ✅
```
→ **整数除法会"丢钱"，所以最后一个商品不做除法，直接吃 `remainDiscount`**，
保证 `Σ明细 == 总优惠`。
→ **为什么要严丝合缝：因为这正是「部分退款」的依据**（面试题 4.5）——
明细合计少 1 元，退款时平台或用户必有一方吃亏。

**第三个要点**：`detailMap.put(id, discount + detailMap.get(id))` 是**累加不是覆盖** ——
多张券可能都作用在同一件商品上（例：商品1 先被券1 减20，又被券3 减20 → 40）。

## 分析：`calculateDiscountDetails`（用户要求单独讲）

**一句话**：把这张券算出的**优惠总额**，按价格占比**分摊到它作用的每件商品**上，并**累加**进 `detailMap`。

**参数**：`detailMap`（账本，**会被就地修改**）/ `courses`（**这张券作用的课程 = availableCourses，不是全部课程**）/ `totalAmount`（折后总价）/ `discountAmount`（本次优惠总额）。返回 `void` —— **副作用型方法**。

```java
int times = 0;
int remainDiscount = discountAmount;
for (OrderCourseDTO course : courses) {
    times++;
    int discount;
    if (times == courses.size()) { discount = remainDiscount; }              // 最后一件：吃剩余
    else { discount = discountAmount * course.getPrice() / totalAmount;      // 按占比
           remainDiscount -= discount; }
    detailMap.put(course.getId(), discount + detailMap.get(course.getId())); // 累加
}
```

### ⚠️ 新观察：分子的「原价」与分母的「折后总价」口径不一致
`discount = discountAmount * course.getPrice() / totalAmount`
- **分子 `course.getPrice()` 是原价**
- **分母 `totalAmount` 是折后总价**（`Σ(price − 已优惠)`）
→ 各商品算出的比例**之和 ≠ 1**，偏差全落在"最后一个商品"身上（靠兜底吸收）。
- **不影响总优惠金额**（兜底保证总和相等），但**影响"每件商品分到多少"→ 退款时每件退多少**。
- 反例：商品A 原价100 已优惠50（现价50）、商品B 原价100 已优惠0（现价100），新券优惠 30
  - 讲义算法（原价占比）：A = 30*100/150 = **20**，B = 30−20 = **10**
  - 若按折后价占比：A = 30*50/150 = **10**，B = 30−10 = **20**（比例之和 = 1，更自洽）
- **定为「值得留意的口径不一致」，不擅自判定为 bug**（讲义例子里 detailMap 全 0 或只剩一件商品，没暴露差异）。

**其他要点**：
- `courses` 只传 `availableCourses` → 分摊**只落在被这张券影响的商品**上，其他商品账本不动 ✅
- `detailMap.put(id, discount + detailMap.get(id))` —— **累加不是覆盖**（多张券可能作用于同一商品）
- 返回 `void` + 就地改 `detailMap` ⇒ **调用方要知道它有副作用**
