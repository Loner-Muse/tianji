## 答疑：`updateById` 是 MyBatis 自带的吗？

用户看到 `CouponServiceImpl.beginIssue` 里的 `updateById(c)`，问是不是 MyBatis 自带的。

**答：不是原生 MyBatis，是 MyBatis-Plus 提供的。**

**调用链**（全部用 javap 从 jar 验证过，mybatis-plus 3.4.3）：
```
CouponServiceImpl extends ServiceImpl<CouponMapper, Coupon>   // 用户代码
  ↓ 继承
com.baomidou.mybatisplus.extension.service.IService
  public default boolean updateById(T);                        // ★ 是 default 方法
  ↓ 内部调 getBaseMapper().updateById(entity)
CouponMapper extends BaseMapper<Coupon>                        // ★ MP 的 BaseMapper
com.baomidou.mybatisplus.core.mapper.BaseMapper
  public abstract int updateById(T);                           // ★ 只有签名，没有实现
  ↓ 实现在 MP 的动态代理里，找对应的 MappedStatement
injector/methods/UpdateById.class                              // ★ 启动时自动注入到每个 Mapper
  ↓
原生 MyBatis 的 SqlSession.update(...)
```
**★ 原生 MyBatis 根本没有 `updateById`** —— 原生只有 `SqlSession` + 你自己声明的 Mapper 接口，
每个方法都要自己写 SQL（XML 或 `@Select`/`@Update` 注解）。

**本项目里两种方法并存，正好对比**：
| 方法 | 来源 | 证据 |
|---|---|---|
| `selectById` / `updateById` / `insert` / `update` / `selectList` | **MP 的 `BaseMapper` 预置**，启动时自动注入 SQL | javap 可见 `BaseMapper.updateById(T)`；`injector/methods/` 下有 17 个方法类（`UpdateById.class` 等） |
| `incrIssueNum` | **自己写的** | `CouponMapper` 上用 `@Update("UPDATE coupon SET issue_num = issue_num + 1 WHERE id = #{couponId} AND issue_num < total_num")` |

### ★★ 两条必须知道的行为特性

**1. `updateById` 只更新「非 null 字段」**（默认策略 `FieldStrategy.NOT_NULL`）
null 字段会被跳过，不生成 `SET`。
→ 这正是 `beginIssue` 敢用半成品对象的原因：
```java
Coupon c = BeanUtils.copyBean(dto, Coupon.class);  // dto 只有 6 个字段，其余全是 null
c.setId(id); c.setStatus(...); updateById(c);      // 名称/折扣等 null 字段被跳过 → 不会被清空
```

**2. id 为 null 会「静默失败」**
`updateById` 生成的 SQL 是 `UPDATE coupon SET xxx WHERE id=?`。
id 为 null → `WHERE id = NULL` 在 SQL 里**恒不成立** → 更新 0 行，**不报错**。
→ 这就是截图里 `c.setId(id)` 那一步必须写的原因（注释也写了「否则 updateById 会因 WHERE id = n...」）。
→ **教训**：`updateById` 的返回值（boolean）被忽略时，失败是完全无声的。

## 答疑：`beginIssue` 里为什么要把时间从 `c` 回填到 `coupon`，不直接用 dto？

用户问："结束时间我直接传 dto 里面的不行吗"

**答：单看结束时间确实等价**（`c = copyBean(dto)`，所以 `c.issueEndTime == dto.issueEndTime`），**但整体不能传 dto**。

**根因：`cacheCouponInfo` 需要 4 个字段，两个对象各缺一半，必须拼**

| 字段 | `dto` | `coupon`（DB 查出来的） | `c`（dto 拷贝 + 补充） |
|---|---|---|---|
| issueBeginTime | ✅（可能是 null） | ✅ 但**是旧值** | ✅ 新值 |
| issueEndTime | ✅ | ✅ 但**是旧值** | ✅ 新值 |
| **totalNum** | ❌ 没有 | ✅ | ❌ 没有 |
| **userLimit** | ❌ 没有 | ✅ | ❌ 没有 |

→ 只能拿 `coupon` 当底（要 totalNum/userLimit），把两个时间从 `c` 回填成新值。
→ 不回填的话，**缓存里存的是 DB 旧时间**（甚至 null），`receiveCoupon` 的时间校验就错了。

**更直白的替代写法（结果相同，但不推荐）**：
```java
coupon.setIssueBeginTime(now);              // 重复了第 4.2 步的赋值逻辑
coupon.setIssueEndTime(dto.getIssueEndTime());
cacheCouponInfo(coupon);
```
缺点是 `now` / dto 的取值逻辑在两处重复，第 4.2 步改了就漏改。
**当前写法的原则：缓存从「将要写库的那个对象 `c`」取值 → 缓存与 DB 天然一致，单一数据源。**

**附带发现**：同一个回填在两处出现，合起来正好覆盖两种发放方式：
- 第 5 步（`isBegin` 时）→ 立刻发放
- 第 6 步（"否则"分支之前）→ 延时发放时也需要，因为 `asyncGenerateCode` 要用新的 `issueEndTime` 当兑换码过期时间
（`isBegin=true` 时第 6 步那次是冗余的，但无害）

## 答疑：`addCoupon` 里的 `couponId` 哪来的？

用户问 `Long couponId = coupon.getId();` 这一行的 couponId 从哪来（新增操作，前端没传 id）。

**答：`save(coupon)` 之后，MyBatis-Plus 把数据库生成的自增主键「回填」到了对象上。**
```java
Coupon coupon = BeanUtils.copyBean(couponFormDTO, Coupon.class);  // coupon.id = null
save(coupon);       // ← 关键：insert 后把 MySQL 生成的 id 回填到 coupon 对象
Long couponId = coupon.getId();   // ← 所以这里能拿到值
```

**根因是 `Coupon` 上的注解**：
```java
@TableId(value = "id", type = IdType.AUTO)   // ← 数据库自增列
private Long id;
```

**★ 本项目三种 id 生成策略的实例（有用的对照表）**：
| IdType | id 从哪来 | 何时 set 到对象上 | 本项目实例 |
|---|---|---|---|
| `AUTO` | **数据库自增列** | **insert 之后**（JDBC `getGeneratedKeys()` 回填） | `Coupon` |
| `ASSIGN_ID` | **MP 用雪花算法生成** | **insert 之前**就 set 好了 | `UserCoupon`（日志里 insert 显式带 id） |
| 序列号当 id | 业务自己算 | 自己 set | `ExchangeCode`（`e.setId(serialNum)`） |

**证据**：2026-09-28 日志里 `UserCouponMapper.insert` 的 SQL 是
`INSERT INTO user_coupon ( id, user_id, coupon_id, ... ) VALUES ( ?, ?, ?, ... )` —— **显式插了 id**，
说明 `UserCoupon` 走的是 `ASSIGN_ID`；而 `Coupon` 是 `AUTO`，insert SQL 里不会有 id 列。

**附带**：`CouponFormDTO` **有** `id` 字段（是给 `updateCoupon` 用的），但 `addCoupon` 走 `copyBean` 会把它一起拷过去 —— 新增场景前端不传，所以是 null，不影响。

**教训**：`save()` 之后主键回填是个很实用的特性 —— 否则新增完想拿到新 id 还得再查一次库。

## 答疑："所有更新操作都是先删除旧数据再更新数据库吗？" → **不是**

用户从 `updateCoupon` 里的 `removeByCouponId(id)` 推广到"所有更新"。

**反证就在 `updateCoupon` 自己身上 —— 同一个方法里两种更新方式并存**：

```java
188: @Transactional
190: public void updateCoupon(Long id, CouponFormDTO dto) {
201:     Coupon c = BeanUtils.copyBean(dto, Coupon.class);
203:     c.setId(id);
205:     updateById(c);                        // ① 主表 coupon：只 UPDATE，不删
209:     scopeService.removeByCouponId(id);    // ② 从表 coupon_scope：先删
216-219:  if (specific) { ...saveBatch(list); }  //    再插（全删重插）
221: }
```

**判断标准 —— 什么时候能用"全删重插"（4 个前提必须同时满足）**：
| 前提 | coupon_scope 满足？ |
|---|---|
| 是**纯关联表/明细表**（表里只有"关系"数据，没有独立生命周期） | ✅ 只有 couponId + bizId |
| id **不被别处引用**（没有外键指向它） | ✅ |
| 删了重插**没有业务副作用** | ✅ |
| 前端传的是**"最终状态"**而非"差异" | ✅ 编辑界面传的是改完之后应该有哪些分类 |

**本质原因**：前端只传"现在应该是 `[101, 330]`"，它**不会告诉你"205 被删了"**。所以后端没有差异信息，只能全删重插。
（替代方案：查询旧值算差集 / 让前端传差异 —— 都更精确但更复杂。）

**反例（不能全删重插的表）**：
- `coupon`（主表）：一行一条记录 → 直接 `updateById` ✅
- `user_coupon`（用户领的券）：用户已持有，绝不能删了重插 → 只能 `updateById` / `lambdaUpdate` 精确改字段

**全删重插的代价 + 为什么必须 `@Transactional`**：
1. id 会变（每次编辑这批记录都拿新自增 id）
2. 性能差（记录多时 N 删 + N 插）
3. **删完、还没插就失败 → 范围数据全丢** → `updateCoupon` 必须 `@Transactional`（第 188 行，已确认有）

**★ 又一个 MyBatis-Plus 坑（已在笔记里记过，此处印证）**：
`removeByCouponId` 的实现是 `baseMapper.delete(new LambdaQueryWrapper<CouponScope>().eq(CouponScope::getCouponId, couponId))`
—— 按**条件**删，不是 `removeById`（按主键删）。删"主表下属的从表记录"必须用条件删。

## 答疑：`categoryCache.getNameByLv3Id(cateId)` 在干嘛

用户在 `queryCouponById` 里问这一步的作用。

**答：把「三级分类 id」翻译成「分类全路径名称」，给前端展示用。**

```java
public String getNameByLv3Id(Long lv3Id) {
    Map<Long, CategoryBasicDTO> map = getCategoryMap();    // ① 拿全量分类（走 Caffeine 缓存）
    CategoryBasicDTO lv3 = map.get(lv3Id);                 // ② 三级
    CategoryBasicDTO lv2 = map.get(lv3.getParentId());     // ③ 用三级的 parentId 找二级
    CategoryBasicDTO lv1 = map.get(lv2.getParentId());     // ④ 用二级的 parentId 找一级
    return lv1.getName() + "/" + lv2.getName() + "/" + lv3.getName();   // ⑤ "后端开发/Java/Java基础"
}
```

**★ 注意：方法名叫 `getName`，返回的却是「一级/二级/三级」全路径**，不是单个名字。

**缓存机制**（`CategoryCacheConfig` + `spring.factories` 自动装配）：
- `Cache<String, Map<Long, CategoryBasicDTO>>`，key 固定 `"CATEGORY"`
- Caffeine：`maximumSize(10_000)`、**`expireAfterWrite(30 分钟)`**
- 未命中 → `categoryClient.getAllOfOneLevel()`（Feign）→ **一次性拉全量分类**
- 设计理由：分类是**总量小、几乎不变、查询极频繁**的字典表 → 拉全量进本地内存，之后全是 map 查找

**为什么必须要"翻译"**：`coupon_scope` 只存 `biz_id`（三级分类 id），**不存名字** ——
名字在课程服务的库里，而且会变；存 id 才不会有冗余和不一致（数据库设计基本原则）。

我当时说"删了会报'优惠券不存在'，提示略差"。但 `queryIssuingCoupons` **只查 `status = ISSUING`**（已确认）→ **已结束的券根本不在券中心显示** → 用户没有入口点它 → 那个提示永远看不到。所以删掉是**纯粹的好处**。

## 答疑：`userId == null ? emptyList() : 查询` 不用三元怎么写

用户在 `queryIssuingCoupons`（第 373-378 行）问这个。

**四种写法**：

**A. if-else（最直白）**
```java
List<UserCoupon> userCoupons;
if (userId == null) {
    userCoupons = Collections.emptyList();
} else {
    userCoupons = userCouponService.lambdaQuery()
            .eq(UserCoupon::getUserId, userId)
            .in(UserCoupon::getCouponId, couponIds)
            .list();
}
```

**B. 抽私有方法（调用处最干净）**
```java
List<UserCoupon> userCoupons = listUserCoupons(userId, couponIds);

private List<UserCoupon> listUserCoupons(Long userId, List<Long> couponIds) {
    if (userId == null) return CollUtils.emptyList();       // 游客天然没有领取记录
    return userCouponService.lambdaQuery()
            .eq(UserCoupon::getUserId, userId)
            .in(UserCoupon::getCouponId, couponIds).list();
}
```

**C. 完全不判（能工作，但不推荐）**
```java
List<UserCoupon> userCoupons = userCouponService.lambdaQuery()
        .eq(UserCoupon::getUserId, userId)          // userId=null → 拼出 user_id = NULL
        .in(UserCoupon::getCouponId, couponIds).list();
```
**★ MyBatis-Plus 关键语义**：`eq(R column, Object val)` 的 condition **默认 true**，
**不会因为 val 是 null 就跳过条件** —— 会拼上 `user_id = ?`（参数 null）→ SQL `user_id = NULL` **恒不成立** → 返回 0 行 = 空列表。
所以**结果是对的**，代价是多一次无用查询 + 隐式依赖 SQL NULL 语义。

**⚠️ 绝对不要写成 `eq(userId != null, UserCoupon::getUserId, userId)`**：
那样 userId 为 null 时会**跳过 user_id 条件** → 查出**所有用户**对这些券的领取记录
→ `issuedMap` 统计成"所有人一共领了多少" → **限领判断彻底错乱**。
（这才是注释里"不要去查 user_coupon"的真正意思 —— 防的不是"查出空"，而是"条件被跳过"。）

**提前 return 方案不推荐**：会让 VO 组装逻辑（第 392-405 行）出现两份，违反 DRY。
